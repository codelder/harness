Create src/tools/read.rs implementing ReadTool following the exact BashTool pattern:

1. **ReadArgs struct** with fields:
   - `file_path: String` (required) - absolute path to read
   - `offset: Option<usize>` - line number to start from
   - `limit: Option<usize>` - number of lines to read

2. **ReadError enum** with thiserror variants:
   - `#[error("Failed to read file: {0}")] IoError(#[from] std::io::Error)`
   - `#[error("Invalid file path: {0}")] InvalidPath(String)`

3. **ReadTool struct** - unit struct like BashTool

4. **Output truncation constant** (CRITICAL - addresses RESEARCH.md Pitfall 3):
   ```rust
   const MAX_OUTPUT_CHARS: usize = 50_000;
   ```
   This prevents context explosion from large file reads.

5. **Tool impl**:
   - `const NAME: &'static str = "read"`
   - `type Error = ReadError`
   - `type Args = ReadArgs`
   - `type Output = String`
   - `definition()` returns ToolDefinition with description explaining offset/limit usage
   - `call()` uses `tokio::fs::read_to_string()` (NOT std::fs - async runtime)
   - Apply offset/limit on lines if provided
   - **Truncation logic** (after applying offset/limit):
     ```rust
     if content.len() > MAX_OUTPUT_CHARS {
         content = format!("{}... (truncated, file too large)", &content[..MAX_OUTPUT_CHARS]);
     }
     ```
   - Return file contents as String

Use `tokio::fs` for all file operations (async). Do NOT use std::fs (blocking).

WHY truncation matters: Large files (e.g., 100KB+ JSON, minified JS) would consume massive context window tokens, leaving little room for agent reasoning. The 50K char limit balances utility with context budget.
