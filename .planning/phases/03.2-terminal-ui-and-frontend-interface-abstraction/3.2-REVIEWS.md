# Cross-AI Plan Review — Phase 3.2

## Summary

These three plans constitute a well-structured corrective architecture pass that addresses the UAT-reported overflow/clipping issues while establishing a clean runtime/frontend protocol boundary. The wave-based dependency ordering is logical (protocol -> runtime wiring -> UI rebuild), and the plans correctly identify that the core problem is protocol shape (correlation IDs, structured snapshots) rather than cosmetic styling. However, there are several gaps around the `ToolCallFinished` event schema, error propagation paths, and the relationship between the existing `FrontendEventSender::flush_best_effort` and the new session-loop wiring.

---

## Strengths

- **Correct root cause analysis**: The plans recognize that overflow/clipping and todo duplication are protocol contract problems, not rendering bugs. Adding `turn_id`, `call_id`, and `TodoSnapshot` at the source is the right approach.

- **Clean dependency ordering**: Wave 1 (protocol) -> Wave 2 (runtime/hook) -> Wave 3 (UI) ensures each layer builds on a stable foundation. Plan 3.2-03 correctly depends on both 3.2-01 and 3.2-02.

- **Protocol-first verification**: Plan 3.2-01 Task 2 requires explicit tests for correlation IDs and snapshots before any UI work begins. This catches contract breaks early.

- **Explicit must_haves and key_links**: Each plan's `must_haves` section maps directly to acceptance criteria, making verification unambiguous.

- **Comprehensive lifecycle coverage in Plan 3.2-03 Task 3**: Adding `TerminalGuard::new()` early-failure rollback tests and best-effort saturation tests addresses SC-5 explicitly.

- **Correct `(turn_id, call_id)` matching logic**: Plan 3.2-03 Task 1 requires matching tool results by tuple, preventing cross-turn correlation bugs when the same tool is called multiple times.

- **Backpressure strategy preserved**: The plans maintain D-02's bounded channel semantics with must-deliver vs best-effort classification.

---

## Concerns

### HIGH Severity

1. **Plan 3.2-01: `ToolCallFinished` event schema inconsistency**
   - The `<interfaces>` block shows `ToolCallFinished` without `name`, but the action says to add `turn_id` and `call_id` without explicitly stating whether `name` stays or goes.
   - Current `src/frontend/protocol.rs` has `ToolCallFinished { name, result_preview }`. If `name` is removed, the reducer cannot display tool identity in the result block header.
   - **Risk**: Reducer may need to look up tool name by `call_id`, which requires maintaining a separate map.

2. **Plan 3.2-02: `TodoUsageHook` constructor signature change is a breaking change**
   - The plan says `TodoUsageHook` takes the active `turn_id: u64` plus the optional `FrontendEventSender`.
   - Current signature is `new(event_tx: Option<FrontendEventSender>) -> (Self, Arc<AtomicBool>)`.
   - Changing this affects `src/llm/provider.rs` and test code that constructs hooks, but the plan does not explicitly call out the test updates needed.
   - **Risk**: Compiler errors in tests may block verification if not anticipated.

3. **Plan 3.2-03: `flush_best_effort()` wiring is underspecified**
   - Task 2 says to pass a live `FrontendEventSender` clone into the UI/session loop and call `flush_best_effort()` after event draining and on draw/tick iterations.
   - Current `src/cli/session.rs` owns the receiver side from `frontend_event_channel`, while the sender is owned by `SessionRuntime`.
   - **Risk**: This requires an explicit ownership design, but the plan does not yet lock down where that sender clone comes from.

### MEDIUM Severity

4. **Plan 3.2-01: No explicit migration path for existing `FrontendEvent` consumers**
   - The plan adds `turn_id` to many event variants but does not show how current consumers compile during the transition.
   - **Risk**: Intermediate commits may not compile, blocking incremental verification.

5. **Plan 3.2-02: `AssistantMessageCompleted.text` must remain plain**
   - The plan correctly says this field stays plain model output only.
   - But current `src/session/runtime.rs` prepends `<reminder>` XML to the response text. The plan should reference that removal more concretely.
   - **Risk**: The old reminder-embedding code may accidentally survive.

6. **Plan 3.2-03: No explicit handling of concurrent tool calls in the same turn**
   - The tuple-based matching implies out-of-order completion support, but the tests do not say so explicitly.
   - **Risk**: Same-turn concurrent tool completion order may be under-tested.

7. **Plan 3.2-02: `Error` event routing is ambiguous**
   - The plan says errors route through `FrontendEvent::Error { turn_id, message }` but does not fully explain where `turn_id` comes from for command-path failures.
   - **Risk**: Error handling may need explicit active-turn tracking in runtime code.

### LOW Severity

8. **Plan 3.2-01: `turn_id = 0` is a convention, not enforced**
   - The plan reserves `turn_id = 0` for session-start snapshots, but that is not type-enforced.

9. **Plan 3.2-03: Banner text `Harness` is hardcoded**
   - Fine for now, but future configurability may want a constant or config path.

10. **Plan 3.2-03: No explicit keyboard help text for the new layout**
    - Status/help copy updates are mentioned, but the exact user guidance is not specified.

---

## Suggestions

1. **Clarify `ToolCallFinished` schema in Plan 3.2-01**
   - Add an acceptance criterion that `ToolCallFinished` retains `name` alongside `turn_id` and `call_id`.

2. **Add explicit test-update guidance in Plan 3.2-02**
   - Note that hook-construction call sites in tests should pass a neutral `turn_id` such as `0` where needed.

3. **Design the `flush_best_effort()` integration point explicitly**
   - Lock down whether backlog flushing happens in runtime, UI loop, or both.

4. **Add explicit removal reference for reminder embedding**
   - Point directly at the existing reminder-embedding path in `src/session/runtime.rs` so it does not linger accidentally.

5. **Add a test case for out-of-order tool completion**
   - Explicitly verify that same-turn multiple tools can finish out of order without mispairing.

6. **Make the `turn_id = 0` convention explicit in code**
   - Consider a named constant like `SESSION_START_TURN_ID`.

7. **Add explicit error-context tracking**
   - Make runtime ownership of active turn context explicit when emitting turn-scoped errors.

---

## Risk Assessment

**Overall Risk: MEDIUM**

The plans are directionally strong and correctly structured, but there are still a few places where execution could stumble if the contract details stay implicit. The largest remaining risks are protocol schema ambiguity, hook-signature fallout in tests, and the exact ownership model for `flush_best_effort()`.

Mitigations already present:
- Clean wave ordering
- Good protocol-first approach
- Strong lifecycle and saturation coverage goals
- Clear requirement mapping to SC-1..SC-5

Recommended pre-execution actions:
- Clarify `ToolCallFinished` schema and whether `name` remains.
- Explicitly design where `flush_best_effort()` is owned and invoked.
- Add a sharper note for removing reminder embedding from assistant text.
