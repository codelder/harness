# Phase 3.2 Implementation Plan Review

## Overview

These 4 plans aim to replace the reedline-based REPL with a ratatui terminal experience while extracting a reusable runtime/frontend architecture. The plans are well-structured with clear wave dependencies and reasonable task decomposition.

## Plan 3.2-01: Extract shared runtime and typed frontend protocol

### Summary
This foundational plan creates the core abstraction layer, a headless `SessionRuntime` and typed `FrontendCommand`/`FrontendEvent` protocol. The approach is sound: extract state ownership from CLI before touching the UI layer.

### Strengths
- Clear separation principle: Making runtime headless first prevents UI concerns from leaking back.
- Protocol-first design: Defining typed enums before implementation ensures clean boundaries.
- Well-scoped tasks: Two focused tasks with clear acceptance criteria.
- TDD approach: Tests for runtime state, turn counter, and protocol construction.

### Concerns
- HIGH: No channel/wiring strategy specified.
  The plan defines `FrontendCommand`/`FrontendEvent` types but does not specify how they will be transported. `CONTEXT.md` mentions `tokio::sync::mpsc`, but the plan should commit to this. Without explicit channel design, Task 2 may produce a runtime that cannot actually emit events.
- MEDIUM: Missing migration path for existing `Session`.
  Current `Session::run()` is called from `main.rs` with specific arguments. The plan says "Keep the existing CLI module compiling" but does not show the interim adapter. There is risk of creating a parallel implementation instead of a migration.
- MEDIUM: Nag reminder logic placement unclear.
  It currently lives in `Session::run()`. The plan does not specify if this stays in runtime or moves to frontend. `CONTEXT.md` says nag is runtime-owned, but the plan should state that explicitly.

### Suggestions
- Add explicit channel types to `protocol.rs`, for example `type CommandSender = mpsc::Sender<FrontendCommand>` and `type EventReceiver = mpsc::Receiver<FrontendEvent>`.
- Specify that `SessionRuntime` exposes a shape like `async fn run(command_rx: mpsc::Receiver<FrontendCommand>, event_tx: mpsc::Sender<FrontendEvent>)`.
- Clarify that nag reminder injection stays in runtime as a state-derived behavior.

### Risk Assessment
MEDIUM. The abstraction is correct but the wiring is underspecified. Without channel semantics, the runtime may not integrate cleanly with later plans.

## Plan 3.2-02: Refactor hook/retry observability into structured events

### Summary
This plan addresses the terminal coupling in `TodoUsageHook` and `with_retry()`. The goal is to replace `eprintln!` calls with typed event emission.

### Strengths
- Targets the right coupling points: `on_tool_call`, `on_tool_result`, and `on_completion_response` all directly write to stderr.
- Preserves hook semantics: Keeps todo detection logic intact while decoupling display.
- Dependency ordering is correct: It depends on 3.2-01 because protocol types are needed first.

### Concerns
- HIGH: Hook trait signature constraint not addressed.
  `TodoUsageHook` implements `rig::PromptHook<M>`. Those trait methods return `ToolCallHookAction` and `HookAction`, not events. Events cannot escape those methods without a side channel such as a channel sender or callback. The plan does not specify how that happens.
- HIGH: Provider/hook interface mismatch.
  `chat_with_history_and_hook()` currently takes `TodoUsageHook` by value. If the hook needs an event sender, the signature changes. This affects `src/llm/provider.rs` and should be reflected more explicitly in the task design.
- MEDIUM: Retry notifications in `with_retry()`.
  Retry notifications are emitted inside a generic helper. Event emission there likely needs either a callback parameter or a more structured return path.
- LOW: Streaming text delta handling is unclear.
  `on_text_delta` currently suppresses output. The plan should clarify whether streaming is expected in ratatui and at what granularity.

### Suggestions
- Define an `EventEmitter` abstraction or closure type that hooks can use.
- Modify hook construction so it receives an event sink alongside the todo usage flag.
- For `with_retry()`, consider surfacing retry metadata back to runtime rather than hardwiring event emission deep in the helper.
- Make `src/llm/provider.rs` more explicit in the task’s file ownership because hook construction happens there too.

### Risk Assessment
HIGH. The `rig-core` `PromptHook` trait is a real technical constraint, and the current plan does not yet describe a complete event-emission path.

## Plan 3.2-03: Implement ratatui CLI adapter and main boot integration

### Summary
This plan introduces ratatui, creates the CLI app state and reducer, and wires it to the runtime. It is the main user-visible deliverable of the phase.

### Strengths
- Reducer pattern: Separating state reduction from rendering enables testing.
- Pane-based layout vision: The "workbench" design is well-scoped.
- Preserves CLI flags: Keeping existing `Args` behavior maintains backward compatibility.

### Concerns
- HIGH: No terminal backend selection specified.
  ratatui still needs a backend such as `crossterm`, `termion`, or `termwiz`. That choice affects async integration and terminal behavior.
- HIGH: Input handling architecture unclear.
  Current CLI uses `spawn_blocking` around reedline. ratatui uses a very different event model. The plan should commit to a tick loop, a dedicated input task, or another explicit structure.
- MEDIUM: Composer state management is underspecified.
  ratatui does not provide a full-featured text editor. Multi-line input, editing, and history all need concrete handling.
- MEDIUM: Graceful shutdown and terminal restoration are not explicit.
  With raw mode TUIs, panic or abrupt exit can leave the terminal broken. The plan should treat restore-on-drop or equivalent as a must-have.
- LOW: Scroll state for long transcripts is not mentioned.

### Suggestions
- Commit to `crossterm` alongside ratatui for Tokio-friendly terminal integration.
- Define the input model explicitly.
- Consider using a text-area widget crate for composer ergonomics.
- Add an explicit task or acceptance criterion for terminal lifecycle and panic recovery.

### Risk Assessment
MEDIUM-HIGH. The integration direction is good, but input handling and terminal lifecycle need more concrete planning to avoid UX regressions.

## Plan 3.2-04: Add migration verification, cleanup, and regression coverage

### Summary
This cleanup plan removes reedline, adds integration tests, and finalizes the migration. It is necessary for ensuring the architectural change does not regress established behavior.

### Strengths
- Protocol-focused testing is the right emphasis.
- Dependency cleanup is explicitly included.
- Clippy validation should catch leftover dead paths and inconsistent APIs.

### Concerns
- MEDIUM: No behavioral equivalence tests specified.
  The plan should explicitly mention multi-turn conversation, tool activity, nag reminder injection, and graceful exit.
- MEDIUM: Missing smoke test for actual CLI startup.
  Library tests alone may miss startup regressions.
- LOW: Error-message preservation is not explicitly verified.

### Suggestions
- Add explicit behavioral test cases to the task list.
- Add a lightweight smoke test such as `harness --help` or a startup-only binary invocation.
- Consider a small behavioral-equivalence test around session lifecycle.

### Risk Assessment
LOW-MEDIUM. The verification plan is sensible but would be stronger with a few concrete runtime-behavior checks.

## Cross-Plan Concerns

### Dependency Chain Risk
- Wave 1 is slightly underdefined because 3.2-02 depends on side-channel semantics that 3.2-01 should probably establish up front.

### Channel Backpressure
- The plans do not yet discuss what happens if runtime emits events faster than frontend consumes them.
- The review recommends a bounded channel and documented overflow behavior.

### Session Restoration
- Persistence is out of scope, but the runtime should avoid painting itself into a corner if later phases need serializable state.

### Test Strategy Gap
- The review recommends strengthening execution checks beyond generic `cargo test` calls.

## Overall Risk Assessment

MEDIUM-HIGH.

Primary risks:
- The `PromptHook` event-emission path is not yet fully designed.
- Channel wiring is underspecified.
- ratatui terminal lifecycle handling is not explicit enough.

Mitigations already present:
- Clear wave structure.
- Good architectural direction.
- Test-oriented task framing.

Recommended pre-execution actions:
- Spike or concretize the `PromptHook` plus event-sink design before implementation.
- Add explicit channel contracts to Plan 3.2-01.
- Add terminal lifecycle handling to Plan 3.2-03.
