# Phase 3.2: Terminal UI and Frontend Interface Abstraction - Context

**Gathered:** 2026-03-25
**Status:** Ready for planning

<domain>
## Phase Boundary

用 `ratatui` 替换当前基于 `reedline` 的交互式 CLI，并把会话运行时和 UI 表现层解耦，形成一个统一的前端接口，让同一套 agent loop 后续可以连接 CLI、Web UI、Desktop 或社交媒体入口。

**Scope:**
- 移除 `Session` 对 `reedline`、`stdout/stderr` 的直接依赖
- 提取共享会话运行时，统一管理消息历史、todo 状态、turn 生命周期和退出逻辑
- 定义 UI 无关的命令/事件接口，优先使用 `tokio::sync::mpsc`
- 将 thinking、tool call、tool result、retry、assistant 输出建模为结构化事件
- 为 CLI 实现 `ratatui` 终端适配器，提供类似 Claude Code 的沉浸式终端体验

**Out of Scope:**
- 真正实现 Web/Desktop/Social 前端
- 修改子代理、多代理、持久化等后续 phase 范围
- 引入浏览器端协议、HTTP API、WebSocket 服务
- 对 LLM provider 行为做功能性扩展（本 phase 只处理展示和运行时边界）

</domain>

<decisions>
## Implementation Decisions

### 运行时与表现层分离

**D-01: 共享运行时必须是 headless 的**

- 当前 `src/cli/session.rs` 同时负责：
  - 读取用户输入
  - 调用 agent loop
  - 管理消息历史和 todo 状态
  - 直接打印响应/错误/总结
- Phase 3.2 必须把这些职责拆开：
  - 共享运行时负责状态和执行
  - CLI 仅负责渲染和收集用户输入

### 统一前端接口

**D-02: 使用 typed channel 协议作为统一接口**

- 前端与运行时之间不直接调用 `println!`/`eprintln!`
- 定义一组 typed enums，例如：
  - `FrontendCommand`：用户输入、提交消息、退出、打断、滚动、切换 pane
  - `FrontendEvent`：assistant delta、thinking、tool started/result、status、error、session summary
- 用 `tokio::sync::mpsc` 作为桥接层，便于：
  - CLI 直接接入
  - 未来 Web/Desktop 用同样事件模型做 transport 适配
  - 社交媒体入口映射为 message-in / message-out
- 采用有界 channel，默认以 `mpsc::channel(64)` 作为初始背压策略
- 事件消费者落后时，必须定义行为：
  - transcript 与最终状态事件不可丢
  - 高频状态/活动事件允许合并或降采样

### agent loop 输出结构化

**D-03: Hook 和重试逻辑只能发事件，不能直接写终端**

- 当前 `TodoUsageHook` 和 `with_retry()` 直接写 `stderr`
- 这会把终端实现硬编码进 agent 层
- 应改为：
  - Hook 将 tool/thinking/text delta 转成 `FrontendEvent`
  - retry 通知也通过事件发出
  - CLI 或其他 adapter 再决定如何呈现
- `PromptHook` 的事件逃逸通过 side channel 完成：
  - hook 内部持有 event sender / sink
  - provider 层负责把 hook 与 runtime 的事件通道接起来
  - `with_retry()` 不直接写终端，而是接收可选的 retry notifier 回调或 sink

### ratatui 只是一个 adapter

**D-04: ratatui 不拥有会话真相**

- ratatui app 维护自己的渲染状态缓存
- 但消息历史、todo 状态、turn 生命周期归共享运行时所有
- 这样 Web/Desktop 可复用同一运行时，而不复制业务逻辑

### 渐进式迁移

**D-05: 保持 CLI 启动参数和单二进制入口稳定**

- 继续使用当前 `main.rs` + `Args`
- 初期仍保持 `harness` 作为唯一入口
- 在现有 CLI 基础上替换 UI 实现，不引入第二套运行方式
- 迁移期间保留一个薄 `Session` 适配层，把旧入口委托到新的 `SessionRuntime`
- nag reminder 继续作为 runtime-owned 行为，不能下沉到 ratatui 视图层

### UX 目标

**D-06: 以“会话工作台”而不是“行编辑器”设计 CLI**

- 目标体验更接近 Claude Code：
  - 主 transcript 区
  - 输入 composer
  - thinking / tool activity 区
  - 状态栏（provider、model、pending work、mode）
- 支持实时事件更新，而不是“等待整轮完成后一次性打印”

### Terminal Runtime Decisions

**D-07: ratatui 使用 `crossterm` 作为 backend**

- 选择 `crossterm` 以匹配 Tokio 环境与跨平台终端事件处理
- 输入事件使用单独的 terminal event task 推送到 command channel
- UI 渲染循环只消费 app state，不在 render path 中做阻塞输入

**D-08: 终端恢复与 panic 安全是 phase must-have**

- 进入 raw mode、alternate screen、mouse capture 的地方必须集中管理
- 退出、错误、panic 三条路径都必须恢复终端
- CLI adapter 需要显式 terminal lifecycle 封装，而不是分散在主循环各处

### Claude's Discretion

- 具体模块命名（`frontend/`、`session/`、`runtime/`）
- ratatui 布局细节和交互键位
- event enum 的细粒度字段设计

</decisions>

<code_context>
## Existing Code Insights

### Current Problems

1. `Session::run()` 同时承担输入、运行时、输出三个层次的职责
2. `agent_loop()` 只返回最终 `String`，无法自然表达实时事件流
3. `TodoUsageHook` 直接 `eprintln!` tool/thinking 信息，导致 agent 层耦合终端
4. CLI 目前只有 line editor，没有 pane、状态栏、异步事件呈现能力

### Reusable Assets

- 现有 `Message` / `AgentTurn` 可作为共享运行时的起点
- `TodoManager` 已经是独立状态对象，适合继续放在 headless runtime 中
- provider 层已有 hook 能力，不需要重写 LLM 调用主路径
- 项目已经统一使用 `tokio`，适合以 async channel 驱动 UI 与 runtime

### Key Migration Constraint

- Phase 3.2 需要把展示相关 side effect 从 `agent`/`llm` 层拔掉，但不能破坏当前 Phase 1-3 已验证的行为：
  - 用户输入 -> 调用 agent
  - nag reminder 注入
  - 错误输出
  - graceful exit

</code_context>

<specifics>
## Specific Ideas

### Shared Interface Sketch

```rust
pub enum FrontendCommand {
    SubmitMessage(String),
    Interrupt,
    Exit,
}

pub enum FrontendEvent {
    SessionStarted { provider: String, model: String },
    UserMessageCommitted { text: String },
    AssistantDelta { text: String },
    AssistantMessageCompleted { text: String },
    Thinking { text: String },
    ToolCallStarted { name: String, args_preview: String },
    ToolCallFinished { name: String, result_preview: String },
    Reminder { message: String },
    RetryScheduled { attempt: u32, max_retries: u32, delay_ms: u64, reason: String },
    Status { text: String },
    Error { message: String },
    SessionEnded { turns: u32, messages: usize },
}
```

推荐补充：

```rust
pub type FrontendCommandSender = tokio::sync::mpsc::Sender<FrontendCommand>;
pub type FrontendCommandReceiver = tokio::sync::mpsc::Receiver<FrontendCommand>;
pub type FrontendEventSender = tokio::sync::mpsc::Sender<FrontendEvent>;
pub type FrontendEventReceiver = tokio::sync::mpsc::Receiver<FrontendEvent>;
```

事件策略：

- must-deliver:
  - `SessionStarted`
  - `UserMessageCommitted`
  - `ToolCallStarted`
  - `ToolCallFinished`
  - `RetryScheduled`
  - `AssistantMessageCompleted`
  - `Reminder`
  - `Error`
  - `SessionEnded`
- best-effort / coalescible:
  - `AssistantDelta`
  - `Thinking`
  - transient `Status`

### ratatui CLI Target

- 左侧或主区域：对话 transcript
- 右侧或底部：thinking / tool activity feed
- 底部 composer：输入框 + 状态提示
- 顶部/底部状态栏：provider、model、todo 提醒、连接状态

### Migration Principle

- 先抽象接口，再接入 ratatui
- 不要把 ratatui 组件逻辑反向渗透回 agent loop
- 先明确 hook side channel 与 terminal lifecycle，再开始大规模迁移

</specifics>
