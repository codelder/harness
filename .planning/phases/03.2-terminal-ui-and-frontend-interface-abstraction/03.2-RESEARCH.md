## User Constraints (from CONTEXT.md)

### Locked Decisions

### 运行时与表现层分离

**D-01: 共享运行时必须是 headless 的**

- 当前 `src/cli/session.rs` 同时负责：
  - 读取用户输入
  - 调用 agent loop
  - 管理消息历史和 todo 状态
  - 直接打印响应/错误/总结
- Phase 3.2 必须把这些职责拆开：
  - 共享运行时负责状态和执行
  - CLI 仅负责渲染和收集用户输入

### 统一前端接口

**D-02: 使用 typed channel 协议作为统一接口**

- 前端与运行时之间不直接调用 `println!`/`eprintln!`
- 定义一组 typed enums，例如：
  - `FrontendCommand`：用户输入、提交消息、退出、打断、滚动、切换 pane
  - `FrontendEvent`：assistant delta、thinking、tool started/result、status、error、session summary
- 用 `tokio::sync::mpsc` 作为桥接层，便于：
  - CLI 直接接入
  - 未来 Web/Desktop 用同样事件模型做 transport 适配
  - 社交媒体入口映射为 message-in / message-out
- 采用有界 channel，默认以 `mpsc::channel(64)` 作为初始背压策略
- 事件消费者落后时，必须定义行为：
  - transcript 与最终状态事件不可丢
  - 高频状态/活动事件允许合并或降采样

### agent loop 输出结构化

**D-03: Hook 和重试逻辑只能发事件，不能直接写终端**

- 当前 `TodoUsageHook` 和 `with_retry()` 直接写 `stderr`
- 这会把终端实现硬编码进 agent 层
- 应改为：
  - Hook 将 tool/thinking/text delta 转成 `FrontendEvent`
  - retry 通知也通过事件发出
  - CLI 或其他 adapter 再决定如何呈现
- `PromptHook` 的事件逃逸通过 side channel 完成：
  - hook 内部持有 event sender / sink
  - provider 层负责把 hook 与 runtime 的事件通道接起来
  - `with_retry()` 不直接写终端，而是接收可选的 retry notifier 回调或 sink

### ratatui 只是一个 adapter

**D-04: ratatui 不拥有会话真相**

- ratatui app 维护自己的渲染状态缓存
- 但消息历史、todo 状态、turn 生命周期归共享运行时所有
- 这样 Web/Desktop 可复用同一运行时，而不复制业务逻辑

### 渐进式迁移

**D-05: 保持 CLI 启动参数和单二进制入口稳定**

- 继续使用当前 `main.rs` + `Args`
- 初期仍保持 `harness` 作为唯一入口
- 在现有 CLI 基础上替换 UI 实现，不引入第二套运行方式
- 迁移期间保留一个薄 `Session` 适配层，把旧入口委托到新的 `SessionRuntime`
- nag reminder 继续作为 runtime-owned 行为，不能下沉到 ratatui 视图层

### 信息架构与布局

**D-06: CLI 必须改成 Claude Code 风格的单列布局，而不是分栏工作台**

- 顶部先显示一个轻量 banner，初始可展示 `Harness`
- banner 下面是统一的展示区，不再拆成独立的 transcript pane 和 activity pane
- 展示区在初始空状态下应当紧贴输入区，看上去像一个自然延展的消息流，而不是预留一大块空白面板
- 输入区位于展示区下方，状态栏位于输入区下方，形成自上而下的单列层级

**D-07: 展示区是单一时间线，随着内容增多向下展开并滚动**

- assistant 回复、thinking、tool call、tool result、todo 变化都在同一个展示区内出现
- 空状态时不强调“面板边界感”，重点是让用户感觉马上就能输入
- 内容增多后通过统一滚动查看历史，而不是让用户在多个 pane 间切换焦点

### 工具事件呈现

**D-08: tool call 和 tool result 必须配对成同一组展示**

- 不再把工具活动作为旁路日志流单独展示
- 每次工具调用都要和对应结果相邻显示，形成一个可扫描的成组 block
- 工具结果摘要应该挂在对应工具调用下面，而不是散落到别的位置
- thinking 也应作为主时间线中的辅助块，而不是独立侧栏

### Todo 呈现

**D-09: todo list 永远固定在展示区最下方，并原位更新状态**

- 当 `todo` 工具被使用后，展示区底部始终保留当前 todo list
- todo 项的完成、进行中、待办状态要在原位置更新，而不是反复追加新的 todo 快照
- todo list 是主展示流的一部分，但在视觉上要稳定锚定在底部，方便持续查看当前计划

### 输入与状态栏

**D-10: 输入区和状态栏的层级必须贴近 Claude Code 的终端心智**

- 输入区保持单行主输入体验，位于最底部交互核心位置
- 状态栏放在输入区正下方，承载 provider、model、token 或 session 状态等摘要信息
- 不再要求用户在 Transcript / Activity / Composer 之间切换焦点才能理解当前会话

### Terminal Runtime Decisions

**D-11: ratatui 使用 `crossterm` 作为 backend**

- 选择 `crossterm` 以匹配 Tokio 环境与跨平台终端事件处理
- 输入事件使用单独的 terminal event task 推送到 command channel
- UI 渲染循环只消费 app state，不在 render path 中做阻塞输入

**D-12: 终端恢复与 panic 安全是 phase must-have**

- 进入 raw mode、alternate screen、mouse capture 的地方必须集中管理
- 退出、错误、panic 三条路径都必须恢复终端
- CLI adapter 需要显式 terminal lifecycle 封装，而不是分散在主循环各处

### Claude's Discretion

- 具体模块命名（`frontend/`、`session/`、`runtime/`）
- banner 的 ASCII 样式、配色和间距细节
- 工具分组 block 的精确视觉样式
- todo list 的符号系统与状态文本
- event enum 的细粒度字段设计

### Deferred Ideas (OUT OF SCOPE)

- WebSocket / HTTP session transport
- Tauri 或原生 desktop shell
- 社交媒体 adapter（Discord / X / Telegram 等）
- 跨 session transcript 持久化
- 多会话 tab / workspace 管理

## Project Constraints (from CLAUDE.md)

- Use `tokio::sync::mpsc` for async channels. Do not use `std::sync::mpsc`.
- Use `tracing` for logging. Do not introduce the `log` crate.
- Use `thiserror` for library errors and `anyhow` for CLI-level errors.
- Do not introduce `async-std`, `crossbeam-channel` in async paths, or `reqwest::blocking`.
- Do not use `unwrap()` in library code; propagate errors with `Result`.
- Keep agent behavior tool-driven. Do not replace the agent loop with prompt-plumbing branches.
- Keep knowledge on demand. Do not stuff UI/runtime rules into giant system prompts.
- Preserve context isolation patterns for future subagents.
- Keep destructive operations behind approval-aware interfaces; the frontend must stay adapter-only.
- Avoid blocking long-running work on the async runtime. Terminal input should stay in a dedicated task.

## Summary

This phase should be planned as a corrective architecture pass, not a cosmetic ratatui restyle. The repository already has a headless `SessionRuntime`, a typed frontend protocol, a ratatui adapter, and protocol-level tests, but the shipped UI still reflects the earlier split-pane workbench and the UAT artifact already reports overflow/clipping problems. The updated intent requires a different reducer model: one single timeline, paired tool blocks, and a pinned todo footer that updates in place.

The key planning implication is protocol shape. The current protocol can emit generic tool events and reminder text, but it cannot robustly support paired tool/result groups or a stable todo footer because it has no tool correlation ID and no structured todo snapshot event. Those are not rendering tweaks; they are runtime-to-frontend contract changes. Plan the work around that boundary first, then implement the single-column ratatui layout over the improved protocol.

Dependency scope should stay conservative. `ratatui` 0.30.0 is current, but it now requires Rust 1.86, while this repo declares `rust-version = "1.75"`. The repo's current `ratatui = "0.29"` / `crossterm = "0.28"` stack already supports the required layout, event loop, and testing primitives, so this phase should not also take an MSRV bump unless that is made an explicit separate decision.

**Primary recommendation:** Keep the repo on `ratatui 0.29.x` and `crossterm 0.28.x`, extend the frontend protocol with correlation and todo snapshot events, and rebuild `CliApp` as a reducer over a single timeline plus pinned footer, verified with protocol tests and targeted `TestBackend` render assertions.

## Architecture Patterns

### Recommended Project Structure
```text
src/
├── frontend/
│   └── protocol.rs      # Typed cross-frontend command/event contract
├── session/
│   └── runtime.rs       # Headless session state and turn lifecycle
└── cli/
    ├── app.rs           # Reducer-owned view state and ratatui rendering
    ├── terminal.rs      # Crossterm lifecycle and input task
    └── session.rs       # Wiring between runtime, channels, and terminal adapter
```

### Pattern 1: Headless Runtime + Typed Frontend Protocol
**What:** `SessionRuntime` owns messages, turn counters, todo state, reminders, and exit semantics; frontends only send `FrontendCommand` and render `FrontendEvent`.
**When to use:** Always. This is the cross-frontend seam for CLI now and web/desktop/social later.
**Example:**
```rust
enum FrontendCommand {
    SubmitMessage(String),
    Interrupt,
    Exit,
}

enum FrontendEvent {
    SessionStarted { provider: String, model: String },
    UserMessageCommitted { turn_id: u64, text: String },
    ToolCallStarted { turn_id: u64, call_id: String, name: String, args_preview: String },
    ToolCallFinished { turn_id: u64, call_id: String, result_preview: String },
    TodoSnapshot { items: Vec<TodoItemView> },
    SessionEnded { summary: FrontendSessionSummary },
}
```
Source: local code audit plus ratatui MVU guidance and Tokio `mpsc` docs. The `turn_id`, `call_id`, and `TodoSnapshot` additions are an inference from current repository gaps.

### Pattern 2: Reducer-Driven Single Timeline
**What:** Model the CLI as a reducer over normalized blocks, for example `Vec<TimelineBlock>`, `Option<AssistantStream>`, `Option<TodoFooter>`, `ComposerState`, and `ViewportState`.
**When to use:** For all UI state that can be reproduced from events. The reducer should not own the canonical conversation or todo truth.
**Example:**
```rust
struct CliApp {
    blocks: Vec<TimelineBlock>,
    pinned_todos: Option<TodoFooter>,
    composer: String,
    scroll: ScrollState,
    status: StatusLine,
}

fn update(app: &mut CliApp, event: FrontendEvent) {
    match event {
        FrontendEvent::ToolCallStarted { call_id, name, args_preview, .. } => {
            app.blocks.push(TimelineBlock::tool(call_id, name, args_preview));
        }
        FrontendEvent::ToolCallFinished { call_id, result_preview, .. } => {
            app.attach_tool_result(&call_id, result_preview);
        }
        FrontendEvent::TodoSnapshot { items } => {
            app.pinned_todos = Some(TodoFooter::from_items(items));
        }
        _ => {}
    }
}
```
Source: [ratatui The Elm Architecture](https://ratatui.rs/concepts/application-patterns/the-elm-architecture/) plus local protocol constraints.

### Pattern 3: Bottom-Anchored Display Area
**What:** Split the visible page into `banner`, `display`, `composer`, and `status`. Inside `display`, render the scrollable timeline above a fixed-height todo footer. Use bottom alignment when content is short so empty state stays visually close to the composer.
**When to use:** For the Claude Code-like single-column layout required by this phase.
**Example:**
```rust
let [banner, display, composer, status] = Layout::vertical([
    Constraint::Length(1),
    Constraint::Fill(1),
    Constraint::Length(3),
    Constraint::Length(1),
])
.areas(frame.area());

let [timeline, todo] = Layout::vertical([
    Constraint::Min(0),
    Constraint::Length(todo_height),
])
.flex(Flex::End)
.areas(display);
```
Source: [ratatui `Flex`](https://docs.rs/ratatui/latest/ratatui/layout/enum.Flex.html) and project-specific layout requirements.

### Pattern 4: Dedicated Terminal Event Task + Centralized Terminal Guard
**What:** Put crossterm input polling in its own task and keep raw-mode / alternate-screen ownership inside one guard object with panic-safe restoration.
**When to use:** Always. Do not read terminal events in the render path.
**Example:**
```rust
let (tx, rx) = tokio::sync::mpsc::channel(32);
let handler = tokio::spawn(async move {
    loop {
        if crossterm::event::poll(timeout)? {
            if let Event::Key(key) = crossterm::event::read()? {
                tx.send(AppEvent::Key(key)).await?;
            }
        }
    }
});
```
Source: [ratatui Terminal and Event Handler recipe](https://ratatui.rs/recipes/apps/terminal-and-event-handler/) and [crossterm `poll`](https://docs.rs/crossterm/latest/crossterm/event/fn.poll.html).

### Anti-Patterns to Avoid
- **Split transcript/activity panes:** Conflicts directly with D-06, D-07, D-08, D-09, and D-10.
- **Pairing tool calls by tool name only:** Breaks as soon as the same tool is called more than once in a turn.
- **Rendering todo as transcript text:** Prevents in-place updates and makes footer anchoring impossible.
- **UI owning conversation truth:** Creates divergence between CLI and future adapters.
- **Relying on unstable ratatui line-count APIs for core layout:** The docs mark `Paragraph::line_count` as unstable; keep stable width/height utilities in repo code.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Async frontend transport | Ad hoc queues or sync channels | `tokio::sync::mpsc` with must-deliver vs best-effort classes | Backpressure and async behavior are already the project-standard pattern. |
| Tool/result pairing | String matching on rendered log lines | Structured `call_id` on tool start/finish events | Name-based matching is ambiguous and breaks grouped rendering. |
| Anchored todo panel | Repeated todo snapshots appended to transcript | Structured `TodoSnapshot` event + pinned footer state | Stable in-place updates require normalized state, not parsed text. |
| Terminal lifecycle | Scattered raw-mode toggles | `TerminalGuard` plus panic-safe restore path | Exit, error, and panic must all restore the terminal. |
| TUI verification | Pixel-perfect screenshot snapshots for everything | Protocol tests plus targeted `TestBackend` assertions | Lower maintenance and directly aligned with the stable architectural boundary. |
| Composer editing | Rebuilding a full reedline-style editor/history stack | Keep a single-line composer for this phase | Matches D-10 and keeps the phase focused on the frontend boundary and layout. |

**Key insight:** The hard parts here are identity, normalization, and lifecycle. If the protocol carries the right structured state, the UI is straightforward. If it does not, the frontend will end up parsing its own logs and re-creating business logic.

## Common Pitfalls

### Pitfall 1: Tool Pairing Without Correlation IDs
**What goes wrong:** Two calls to `read`, `bash`, or `todo` in the same turn become impossible to pair correctly in the UI.
**Why it happens:** The current protocol only carries `name` and preview text, even though the hook callbacks expose per-call identity inputs.
**How to avoid:** Add `call_id` to `ToolCallStarted` and `ToolCallFinished`. Prefer the provider/tool call ID and fall back to the internal call ID when needed.
**Warning signs:** Grouped tool blocks show the wrong result under the wrong call or merge repeated calls together.

### Pitfall 2: Anchored Todo Built as Timeline Messages
**What goes wrong:** Todo state keeps duplicating in the scrollback and cannot stay visually pinned at the bottom.
**Why it happens:** The current runtime exposes reminder text and tool activity, but not a structured todo snapshot.
**How to avoid:** Emit `TodoSnapshot` from runtime-owned state after successful todo writes, then render it separately as a pinned footer.
**Warning signs:** The UI appends repeated todo dumps or tries to parse the todo tool's string output.

### Pitfall 3: Wrapped-Content Scroll Math Breaks on Resize
**What goes wrong:** Long content disappears, clips, or lands on the wrong scroll offset after terminal resize.
**Why it happens:** Scroll offset is based on rendered line count, not raw string length. Wrapped height changes with width.
**How to avoid:** Keep one shared line-count utility for layout math, recompute max scroll on every draw, and clamp offsets after resize.
**Warning signs:** UAT reports "content past pane size is not shown" or scroll-to-end stops following new content.

### Pitfall 4: Terminal Restore Only Happens on Happy Path
**What goes wrong:** Raw mode or alternate screen leaks into the user's shell after a panic or early return.
**Why it happens:** Lifecycle code gets spread across session boot, render loop, and shutdown logic.
**How to avoid:** Keep all terminal ownership in `TerminalGuard` and install a panic restore path if this phase touches panic handling.
**Warning signs:** Cursor remains hidden, shell echo is broken, or the prompt renders inside the alternate screen after failure.

### Pitfall 5: Best-Effort Event Backlog Never Flushes
**What goes wrong:** Streaming deltas and status events stop appearing under sustained output.
**Why it happens:** Bounded best-effort queues coalesce correctly, but the reducer/render loop never flushes the backlog at stable points.
**How to avoid:** Flush best-effort backlog after draining must-deliver events and after each draw/tick.
**Warning signs:** Final assistant message appears, but intermediate deltas or thinking blocks vanish during busy turns.

## Open Questions

1. **Should event identity stop at `call_id`, or should all runtime events also carry `turn_id`?**
   - What we know: Tool pairing needs `call_id`. Session/runtime already tracks turns locally.
   - What's unclear: Whether future web/desktop adapters need every event keyed to a turn for replay/debugging.
   - Recommendation: Add both `turn_id` and `call_id` now. The cost is low and it avoids another protocol break later.

2. **When should `TodoSnapshot` be emitted?**
   - What we know: Stable pinned rendering needs normalized todo state from `TodoManager`.
   - What's unclear: Whether snapshot emission should occur only on successful todo writes or also on session start/end.
   - Recommendation: Emit on session start, after every successful todo mutation, and after any reminder-triggering turn if the list is non-empty.
