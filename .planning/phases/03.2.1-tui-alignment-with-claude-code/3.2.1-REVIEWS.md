# Cross-AI Plan Review — Phase 3.2.1

## Codex Review

### Summary

The phase intent is good and mostly aligned with the stated UX target, but the plans are not independent in the way they're written. Three shared seams drive most of the risk: terminal lifecycle in `src/cli/terminal.rs:19`, timeline rendering in `src/cli/app.rs:318`, and protocol/runtime event ownership in `src/frontend/protocol.rs:61` plus `src/session/runtime.rs:127`. The main gap is that several plans assume data or rendering primitives that do not exist yet, so if executed as-is they will either expand scope mid-phase or land as partial implementations.

### Cross-Plan Strengths

- The file targeting is mostly sensible: terminal, app reducer, protocol, and runtime are the right areas.
- The plans preserve current architecture instead of bypassing it with ad hoc CLI-only state.
- Best-effort vs must-deliver event thinking in the protocol is already strong, and Plan 07 builds on that instead of inventing a parallel channel.
- The phase goals are concrete and testable from a user-facing perspective.

### Cross-Plan Concerns

- **[HIGH]** Plans 02 and 04 both depend on a render-model refactor. The timeline is currently rendered as one `String` into one `Paragraph`, so semantic per-message coloring is not achievable with only a `style_for_block` helper.
- **[HIGH]** Plans 03 and 07 both mutate the statusline contract, but neither defines how spinner text, actual runtime status, and token usage coexist without fighting for the same line.
- **[HIGH]** Plan 05 misses the real `SessionStarted` emitter. That event is emitted from `SessionRuntime`, not `cli/session.rs`, so the file list and ownership are off.
- **[MEDIUM]** Plan 01 changes viewport mode, but none of the plans specify viewport height strategy, resize handling, or whether the current 50ms redraw loop is acceptable in inline mode.
- **[MEDIUM]** Plan ordering is underspecified. Recommended order is `01 → 05 → shared render refactor for 02/04 → 06 → 03/07`.

### Plan 01: Inline Viewport Mode

**Summary**
Good direction and the right place to start, but the plan is too narrow for ratatui inline mode.

**Strengths**
- Correctly targets `terminal.rs`.
- Removes mouse capture, which fits the new mode.

**Concerns**
- **[HIGH]** It does not define how `Viewport::Inline(height)` gets its height or adapts on resize.
- **[MEDIUM]** `TerminalGuard` state is built around alternate-screen ownership; tests should be rewritten around generic lifecycle cleanup, not just patched.
- **[MEDIUM]** Inline mode may make the current frequent redraw loop more visible or more expensive.

**Suggestions**
- Add explicit acceptance for resize behavior and viewport height selection.
- Rename lifecycle state away from alternate-screen semantics to avoid a half-migrated abstraction.

**Risk Assessment:** `MEDIUM` — the core change is localized, but the missing height/resize behavior can make the UX regress badly.

---

### Plan 02: Color System

**Summary**
Conceptually right, but incomplete against the current render path.

**Strengths**
- `theme.rs` is a clean boundary.
- Semantic color naming is preferable to inline color constants.

**Concerns**
- **[HIGH]** `CliApp` currently renders timeline content as plain text; block-level styles will not color user/assistant/tool/thinking lines independently.
- **[MEDIUM]** Acceptance criteria only say "existing tests pass"; they do not verify rendered style output.
- **[LOW]** The plan does not define fallback behavior for terminals with limited color support.

**Suggestions**
- First refactor timeline rendering to `Vec<Line>` or `Vec<Span>`-based output.
- Add render assertions for at least banner, statusline, composer, and one message type per semantic color.

**Risk Assessment:** `HIGH` — the planned implementation path does not actually satisfy REQ-3.2.1-02 without structural render changes.

---

### Plan 03: Spinner Animation

**Summary**
Reasonable scope, but the spec and implementation language are currently inconsistent.

**Strengths**
- A separate `spinner.rs` keeps animation state out of `CliApp`.
- The existing 50ms UI tick can drive animation without adding another task.

**Concerns**
- **[MEDIUM]** The proposed frames are not ASCII; they are Unicode symbols.
- **[MEDIUM]** No cadence, determinism, or test strategy is specified.
- **[MEDIUM]** Fun messages can overwrite meaningful runtime status unless precedence rules are defined.

**Suggestions**
- Decide whether the requirement is truly ASCII or intentionally Unicode.
- Define statusline composition: `spinner + real status + token stats`, with real errors/retries taking priority.

**Risk Assessment:** `MEDIUM` — it is easy to ship something flashy but semantically noisy.

---

### Plan 04: Simplified Message Format

**Summary**
Strong alignment with the UX goal, but the acceptance criteria are too weak.

**Strengths**
- Directly addresses visible verbosity in the current transcript.
- Covers streaming output, not just finalized messages.

**Concerns**
- **[MEDIUM]** It does not define formatting for `Reminder`, `Error`, and `Status` notes, which still currently include labels and sometimes turn IDs.
- **[MEDIUM]** "No `You [` in production code" is a brittle acceptance check.
- **[MEDIUM]** Tool formatting likely wants the same render-model work needed by Plan 02.

**Suggestions**
- Add golden-render tests for user, assistant, thinking, tool, note, and streaming blocks.
- Keep turn IDs internally, but remove them from display consistently across all block types.

**Risk Assessment:** `MEDIUM` — the goal is clear, but it overlaps heavily with the unfinished render refactor from Plan 02.

---

### Plan 05: Enhanced Banner

**Summary**
The feature is right; the current ownership is wrong and the requirement mapping is incomplete.

**Strengths**
- Extending startup metadata is the right mechanism.
- Banner enhancement belongs in `CliApp`.

**Concerns**
- **[HIGH]** `SessionStarted` is emitted from `SessionRuntime`, so changing only `cli/session.rs` will not work.
- **[MEDIUM]** The plan's acceptance says one-line banner, while the requirement says multi-line info panel with notifications.
- **[MEDIUM]** `working_directory` is CLI/session metadata, not model-runtime metadata; pushing it into runtime can over-couple the protocol.

**Suggestions**
- Either extend `SessionStarted` in `SessionRuntime` properly, or introduce a separate CLI-owned metadata event.
- Reconcile the requirement: single-line compact banner or multi-line panel. Right now the plan claims both.

**Risk Assessment:** `HIGH` — the current file ownership is incorrect and the acceptance criteria underdeliver relative to REQ-3.2.1-05.

---

### Plan 06: Dynamic Todo Display

**Summary**
This is the cleanest plan of the set, but it needs clearer transition rules.

**Strengths**
- Fits the reducer model well.
- Uses protocol events already in place instead of inventing UI polling.

**Concerns**
- **[MEDIUM]** `todo_was_active` alone may duplicate summaries if multiple completed-only snapshots arrive.
- **[MEDIUM]** The plan does not define behavior for "all completed" vs "todo list becomes empty".
- **[LOW]** It does not specify whether completed summaries should include counts, item text, or turn context.

**Suggestions**
- Track previous visibility state plus previous snapshot hash/content, not just a boolean.
- Add tests for `active → completed`, `completed → completed`, `completed → new pending`, and `active → empty`.

**Risk Assessment:** `LOW-MEDIUM` — the scope is local and the behavior is already event-driven.

---

### Plan 07: Enhanced Statusline

**Summary**
This is the riskiest plan because the data source is not actually available at the proposed layer.

**Strengths**
- Reuses the frontend protocol and backlog design appropriately.
- Token display belongs in statusline, not in the transcript.

**Concerns**
- **[HIGH]** `SessionRuntime` does not own token usage data; `agent_loop`/`LlmProvider` would need to surface it first.
- **[HIGH]** "actual or placeholder" is a dangerous acceptance escape hatch and will likely produce misleading UX.
- **[MEDIUM]** REQ-3.2.1-07 mentions context information, but the plan only covers `N in / M out`.

**Suggestions**
- Do not start this until the LLM/provider layer can expose real usage data or explicitly mark the phase as blocked on provider support.
- Define event semantics as cumulative totals, not per-turn deltas, so best-effort coalescing remains correct.

**Risk Assessment:** `HIGH` — the plan underestimates the interface changes required below `SessionRuntime`.

---

## Overall Suggestions

1. **Merge Plans 02 and 04** into one "timeline render model" plan before styling or format tweaks.
2. **Keep Plan 05 honest about ownership**: runtime-emitted event or new CLI metadata event, not both.
3. **De-scope Plan 07** unless real token usage is confirmed in `rig-core`/provider responses.
4. **Tighten acceptance criteria** around rendered snapshots, not just symbol searches or compilation.

## Overall Risk Assessment

**`MEDIUM-HIGH`**. Plans 01 and 06 are straightforward, but Plans 02, 05, and 07 currently have structural gaps that will likely cause replanning during implementation. The phase is viable if the team treats rendering and event ownership as first-class dependencies instead of seven isolated patches.
